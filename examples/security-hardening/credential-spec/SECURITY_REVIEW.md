## Overall assessment

The credential draft already distinguishes cryptographic validity from issuer authorization, defines R-DID privacy requirements, pins VWC digest canonicalization, and separates credential validity from task completion. The remaining hardening work is concentrated in optional or governance-derived semantics: membership consent, lifecycle/status, exact witness binding, presentation replay, ZKP profiles, invitation redemption and verifier non-inference rules.

## Security controls already present

- Every credential proof must be cryptographically verified before reliance.
- Issuer authorization is explicitly separate from signature validity.
- VWC digest canonicalization is fixed to JCS + SHA-256 when used.
- R-DID uniqueness is mandatory for pairwise relationships.
- taskContext-bearing credentials cannot alone prove task completion.
- The specification explicitly says VEC signatures do not establish truth and PHC is governance-derived.

| `spec/body.md#governance-considerations` | Witnessing policies are delegated to governance. |

**Attack / failure path**

A low-assurance or malicious witness labels its method with a high-assurance term. A verifier checks signature and string value but not the witness's accreditation, procedure, device or evidence requirements.

**Existing mitigations**

- Issuer authorization must be evaluated through governance/trust registry.
- The spec intentionally does not claim the witness proves more than its attestation.

**Residual gap**

The schema provides no machine-readable assurance profile identifier or evidence-policy binding for witness methods.

**Recommended hardening**

Define governed witness-method profiles with stable identifiers, issuer eligibility, evidence requirements, liveness/proximity semantics and audit expectations. Human-readable method strings should not drive authorization.

**Verification / closure evidence**

- Verifier rejects a high-assurance predicate when the VWC lacks a recognized witness profile/authorized issuer.

| RAHP guardrails | [GR-16 — Formal Threat Model Publication](../../../build/site/catalogue.html#GR-16) |
| RAHP assurance tests | [AT-16 — Published threat model exists, is dated within 12 months, and covers all six listed threat…](../../../build/site/catalogue.html#AT-16) |

**Preconditions**

- Verifier supports both VC Data Model 1.1 and 2.0.
- Producer can choose the older model/proof combination.

**Evidence**

| Source | Observation |
|---|---|
| `spec/body.md#w3c-verifiable-credentials-version-support` | Implementations MUST verify v2.0 and SHOULD accept v1.1; issuers may use v1.1 for compatibility. |
| `spec/body.md#property-mapping` | The text presents a simple property mapping while proof types are chosen from those commonly used in both versions. |

**Attack / failure path**

An attacker or weak issuer selects the least restrictive supported combination of data model, context and proof suite, causing inconsistent canonicalization, proof processing or status behavior across verifiers.

**Existing mitigations**

- v2.0 is the primary standard.
- Implementations are told to process proof types required by both versions.

**Residual gap**

No named minimum cryptographic profile or downgrade policy accompanies dual-version acceptance.

**Recommended hardening**

Define minimum accepted proof suites and algorithm-agility rules per VC version; allow deployments to disable legacy issuance/verification by policy and prohibit silent fallback after v2 verification failure.

**Verification / closure evidence**

- Downgrade tests prove a failed v2 proof is not retried as a weaker legacy interpretation and deprecated suites are rejected.
