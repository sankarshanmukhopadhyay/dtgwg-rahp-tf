# v1.5 release runbook

This runbook defines the final governed steps for cutting RAHP Toolkit v1.5.0 after the release-qualification branch has passed all required gates.

The release decision is evidence-based. A green pull request is necessary but not sufficient unless the machine-readable qualification contract at `method/v1.5-release-qualification.yaml` also passes.

## Preconditions

Before cutting v1.5.0, confirm:

1. `python3 tools/validate_v15_release.py` passes;
2. the full repository validation workflow passes;
3. the GitHub Pages build and rendered-coverage validation pass;
4. `rahp-engine-contract-v1`, normalized result schema version `1`, and `rahp-evidence-retention-v1` remain unchanged;
5. all v1.5 capabilities are registered in `method/capability-documentation.yaml` and their rendered documentation is synchronized;
6. the deployment-neutral fixtures pass independently of project-specific profiles;
7. no unresolved release-blocking policy gate remains `FAIL` or `INDETERMINATE`;
8. the actor performing publication has explicit `publish` authority for the release scope.

## Release-name selection

At release-preparation time, select one butterfly species at random from the recorded source:

`https://en.wikipedia.org/wiki/List_of_butterflies_of_West_Bengal`

Record the selected common name and scientific name in the v1.5.0 release notes. The butterfly name is human-readable release metadata; SemVer `v1.5.0` remains the compatibility identifier.

Do not preselect the butterfly before the release is otherwise ready to cut.

## Final release commit

The release-cut commit SHOULD be small and mechanical. It should:

- change package/workspace versions from `1.2.0` to `1.5.0`;
- set `PROJECT-STATUS.yaml` stable release to `1.5.0` and release status to `released`;
- update `method/versioning.yaml` stable release to `v1.5.0`;
- update the README release banner and current-release links;
- add/finalize `docs/releases/v1.5.0.md` including the selected butterfly name;
- add the `v1.5.0` CHANGELOG entry;
- update any portable release fixture that records the toolkit version;
- rebuild generated evidence if required; and
- rerun release metadata, full validation and Pages checks.

No semantic method change should be introduced in the release-cut commit. If a semantic change is needed, it belongs in a separate reviewed PR followed by qualification again.

## Tag and publication

After the final release commit is merged and all gates are green:

1. create tag `v1.5.0` at the exact qualified release commit;
2. create the GitHub release from that tag;
3. use the same butterfly common/scientific name in the GitHub release title/body and repository release notes;
4. publish the release only with explicit `publish` authority;
5. verify the rendered documentation and release links after publication.

## Evidence retained

The release record should retain or link to:

- the qualification PR and merge commit;
- successful validation and Pages runs;
- the machine-readable v1.5 qualification manifest;
- the final release commit SHA;
- the release tag;
- the selected butterfly identity and source;
- any gate evaluation used for the release decision; and
- the authority basis for publication.

This evidence makes the release itself an executable-governance event rather than an unrecorded maintainer action.
