# RAHP Toolkit v1.2.0 — Evidence-Driven Assurance

Released: 2026-08-20

RAHP v1.2.0 establishes an **evidence-driven assurance lifecycle** above the stable v1 engine contract. Detector output is treated as a signal rather than an automatic finding: typed evidence, credited controls, assurance evidence and target context determine the residual assurance conclusion.

The release preserves the v1 compatibility boundary while making assurance conclusions substantially more precise, auditable and retestable.

## Core assurance invariant

> A detected risk signal does not become an assurance finding until RAHP evaluates relevant control evidence, assurance evidence, target context and the residual gap.

This allows RAHP to distinguish a vulnerable target from a mature target that exposes the same risk surface but already implements effective controls.

## Added

### Typed assurance evaluation

RAHP now defines first-class assurance evaluations with seven residual states:

| State | Meaning |
|---|---|
| `assured` | Required assurance propositions are supported by sufficient evidence. |
| `controlled` | A relevant risk exists, but effective controls and assurance evidence are present. |
| `finding` | Evidence supports an actionable residual defect. |
| `assurance-gap` | A control or property may exist, but the required assurance evidence is incomplete. |
| `review-required` | Automation cannot safely determine the assurance conclusion. |
| `not-assessed` | The proposition was not sufficiently evaluated. |
| `not-applicable` | The proposition is outside the applicable target scope. |

The canonical schema is `method/schema/assurance-evaluation.schema.json`.

### Evidence classification and control credit

Evidence is classified independently by context and authority. Context classes include normative specification, implementation, test, deployment, governance, operational evidence, build infrastructure, documentation, example and historical material. Authority classes include normative, authoritative, supporting, informative and incidental evidence.

This prevents incidental repository signals from being assigned the same assurance weight as normative requirements, implementation controls or conformance tests, and makes **control credit** a first-class part of the evaluation.

### Zero-finding semantics

`0 findings` is no longer implicitly equivalent to an assurance pass. A normalized result may report zero findings while retaining unresolved `assurance-gap`, `review-required` or `not-assessed` states. The v1 engine validator prevents such a result from being dispositioned as `no-material-assurance-impact` without resolving those states.

### DRARM integration

The Distributed Resilience and Amplification Risk Model now maps resilience signals into portable RAHP `RKP-*`, `CTP-*`, `GRP-*` and `ATP-*` patterns where semantic equivalence exists. Rules without an exact portable mapping remain explicitly unmapped rather than being forced into a misleading graph relationship.

The mapping lives at `method/mappings/resilience-to-assurance.yaml`.

### Governed remediation manifests

`method/schema/remediation-manifest.schema.json` defines a machine-readable boundary between an assurance conclusion and remediation work. A remediation record can identify the responsible control or authority plane, requested outcomes, required evidence and publication posture without granting automatic authority to modify an assessed or upstream repository.

Observation permission, assessment permission and publication permission remain distinct capabilities.

### Evidence-based retesting

`method/schema/retest.schema.json` defines retest records that correlate prior findings and revisions with a new reviewed revision and closure evidence. Normalized transitions include `finding → controlled` as `resolved` and `controlled → finding` as `regression`.

Issue closure can therefore be tied to evidence rather than discussion status alone.

## Engine and implementation changes

- `rahp-engine-contract-v1` gains additive assurance-evaluation, remediation and retest operations without changing its contract identifier.
- Normalized result schema version `1` gains optional `assurance_summary`, `evaluations`, `remediations` and `retests` structures; existing v1.1 results remain valid.
- Python reference support is provided through `tools/assurance.py`, `tools/assurance_cli.py` and the extended engine validator.
- TypeScript schema/core/CLI reference implementations expose the same assurance states, summary behaviour and retest semantics.

## Conformance evidence

v1.2 adds fixtures for three materially different assurance outcomes:

1. risk signal + present control + incomplete assurance evidence → `assurance-gap`;
2. risk signal + absent control → `finding`;
3. risk signal + present control + passing assurance evidence → `controlled`.

Additional fixtures validate remediation manifests, retest records and v1.2 normalized-result extensions across the Python and TypeScript reference implementations.

## Compatibility

The stable compatibility boundaries remain:

```text
rahp-engine-contract-v1
normalized result schema version 1
rahp-evidence-retention-v1
```

v1.2 is an additive minor release. Existing v1.1 normalized results and deployment profiles remain valid. A future breaking change to the method or normalized-result contract requires the versioning rules defined in `method/versioning.yaml`.

## Governance boundary

v1.2 intentionally does **not** turn RAHP into a cross-repository issue bot. Remediation manifests may identify an owning repository or upstream control plane, but publication remains a separately authorized governance action. External repositories fail closed when publication authority is absent.

## Validation
