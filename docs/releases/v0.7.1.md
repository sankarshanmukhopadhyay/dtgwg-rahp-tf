# v0.7.1 — Assessment Queue Consolidation

v0.7.1 is a focused operational-assurance release. It does not expand the portable
RAHP method. It fixes how deployment observations become accountable assessment work.

## Why this release exists

The first live DTG queue demonstrated that repository drift and selected upstream
issue activity can describe the **same underlying assessment need**. Treating every
observation as a separate GitHub issue creates duplicate work and makes the issue
queue look larger than the actual assurance backlog.

v0.7.1 therefore separates event identity from assessment identity.

```text
source
  -> observation
  -> trigger
  -> assessment
  -> finding
  -> disposition
  -> reviewed baseline
```

## Stable assessment identity

Repository assessment keys are independent of SHA:

```text
dtg:repository:trustoverip/dtgwg-trust-tasks-tf
```

Selected upstream issues receive their own trigger key plus a repository correlation
key:

```text
dtg:issue:trustoverip/dtgwg-trust-tasks-tf#204
          |
          +-> dtg:repository:trustoverip/dtgwg-trust-tasks-tf
```

The publisher first looks for an open correlated repository assessment. If one exists,
the new observation is appended to that work item. If it does not, the publisher can
use the selected-issue key as a standalone assessment identity. Closed assessment
cycles are not reused: a later material change starts a new cycle.

The publisher recognizes the v0.7 `rahp-dtg-change` marker as a migration input so
already-open DTG issues can be coalesced without manual retagging.

## Initial queue disposition

Two durable DTG reviews close the first generated queue:

| Assessment | Target | RAHP issues | Reviewed revision | Disposition |
|---|---|---|---|---|
| `DTG-AR-2026-001` | Trust Tasks | #1, #3, #4 | `8eb7509` | findings raised; no blocking defect |
| `DTG-AR-2026-002` | Verifiable Trust Infrastructure | #2 | `1c20e31` | findings raised; operational assurance follow-up |

The Trust Tasks review deliberately advances beyond the intermediate SHA that opened
issue #1. This prevents a review of `fbe196a -> bcc75f5` from immediately being made
stale by the subsequent framework/security commits. The reviewed window instead ends
at `8eb7509` and records the intermediate revision as superseded within the same
assessment cycle.

Watched Trust Tasks issue #204 remains open upstream and continues to be a future
reassessment trigger when its discussion produces normative repository changes.

## Behavioural changes

- repository monitors emit stable `assessment_key` values;
- selected-issue monitoring emits both `assessment_key` and
  `related_assessment_key`;
- the publisher indexes open issues by embedded assessment markers rather than exact
  title alone;
- legacy DTG issue markers are translated into stable repository keys;
- repeated observations are appended with idempotent trigger markers;
- repository events may advance the title/revision of the open work item rather than
  opening another issue;
- durable review records explicitly identify the reviewed SHA and disposition.

## Compatibility

This is an operational refinement of v0.7.0. Existing deployment profiles, RAHP data,
review modes and portable CLI behaviour remain compatible. Deployments that do not use
GitHub issue publication do not need to adopt the queue state model.

## Next

The stable execution concepts established here are intended to be inputs to v0.8's
engine-boundary work. v0.8 should implement this lifecycle rather than inheriting the
older assumption that a change event and an assessment are the same object.
