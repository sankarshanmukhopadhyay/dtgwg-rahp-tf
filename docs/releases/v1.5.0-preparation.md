# RAHP Toolkit v1.5.0 — Continuous Governed Assurance

**Status:** release-preparation content; not yet the published v1.5.0 release notes.  
**Release name:** selected at random from the West Bengal butterfly list only when the release is otherwise ready to cut.

This page is the synchronized content baseline for the final `docs/releases/v1.5.0.md`. It may be promoted into the final release notes by the mechanical release-cut commit after qualification succeeds.

## Release thesis

RAHP v1.5 evolves the toolkit from evidence-driven point-in-time assessment into **Continuous Governed Assurance**.

The stable v1.2 question was:

> What assurance conclusion does the available evidence support?

v1.5 adds the operational question:

> How does that conclusion remain governed, reviewable and current as the target, evidence, controls and authority state change?

The answer is a portable lifecycle with durable identity, explicit change impact, evidence provenance, freshness, remediation/retest, policy evaluation, scoped authority and actionable posture.

## Major capabilities

### Durable assurance lineage

Assessments have stable identities independent of an individual run or issue tracker. Findings can persist, consolidate, split, resolve, regress, be reclassified or be superseded without losing history.

### Governed remediation and retest

A finding can become a remediation obligation with acceptance criteria, evidence requirements and retest triggers. Detector silence is not closure. Closure and risk acceptance remain separately authorized governance actions.

### Assurance graph and impact analysis

RAHP can represent dependencies among targets, requirements, controls, evidence, tests, assessments, findings and remediations. Explicit edge propagation semantics identify affected assessments after material change without treating graph reachability as a finding.

### Evidence provenance, freshness and assurance delta

Evidence can carry source revision, producer, workflow, observation time, integrity and authority metadata. Prior assurance can become potentially stale, stale, retest-required, superseded or indeterminate. Reassessment produces a machine-readable delta rather than silently overwriting history.

### Executable authority and policy gates

Authority grants independently scope actions such as observe, assess, disposition, remediate, publish, accept-risk, close and reopen. Suspension, revocation and expiry are executable states. Policy gates return `PASS`, `FAIL` or `INDETERMINATE`; a gate never creates authority.

### Portable assurance posture

Operational and portfolio views expose conclusion, freshness, remediation, gate, authority, change and evidence-gap state directly. RAHP does not produce a synthetic universal assurance score.

### Release qualification as assurance evidence

`method/v1.5-release-qualification.yaml` and `tools/validate_v15_release.py` make the v1.5 release boundary testable. The release candidate must preserve stable v1 contracts, pass neutral fixtures, keep documentation synchronized, prove work-item-independent reconstruction, retain deployment independence and pass the repository/Pages suites.

## Compatibility

v1.5 is additive across the stable v1 boundary:

```text
rahp-engine-contract-v1
normalized result schema version 1
rahp-evidence-retention-v1
```

Existing v1.1/v1.2 normalized results remain valid. No project-specific deployment becomes a required core dependency.

## Portability evidence

The canonical v1.5 conformance path uses a fictional payments specification and generic work tracker. Project-specific DTG, CAWG/C2PA and other assessments remain demonstrations of the portable contracts rather than normative inputs to them.

The qualification suite also verifies that deleting operational work-item state does not destroy the canonical assessment lineage.

## Governance boundaries retained

v1.5 does not authorize RAHP to:

- accept risk automatically;
- publish externally merely because a gate passes;
- close a remediation because a detector stopped firing;
- infer non-impact from an incomplete assurance graph;
- infer current assurance from missing freshness evidence;
- treat repository permissions as governance authority; or
- collapse uncertainty into a binary success state.

## Release qualification checklist

The release is ready to cut only when all of these are green together:

- portable lineage validation;
- remediation/retest validation;
- assurance graph/impact validation;
- provenance/freshness/delta validation;
- authority/policy-gate validation;
- portable posture validation;
- capability/documentation synchronization;
- work-item-independent lineage reconstruction;
- stable Python/TypeScript engine conformance;
- portable instance validation;
- maintained deployment demonstration checks;
- generated-evidence freshness;
- reference-link validation;
- Just the Docs build and rendered Pages coverage; and
- `python3 tools/validate_v15_release.py`.

## Final release-cut changes

The final release commit should contain no new method semantics. It should only:

1. select and record the random West Bengal butterfly common/scientific name;
2. bump package/workspace/release metadata to `1.5.0`;
3. promote this content to `docs/releases/v1.5.0.md` and update `CHANGELOG.md`;

6. rerun all qualification, validation and Pages gates;
7. tag the exact qualified commit `v1.5.0`; and
8. publish the GitHub release under explicit publication authority.
